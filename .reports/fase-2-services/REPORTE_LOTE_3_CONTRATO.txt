DECISIONES DESVIADAS DEL PLAN ORIGINAL

D1 — Prefijo RUC por test file para evitar colisiones en ejecución paralela.
  Vitest corre los archivos de test en paralelo. Los RUCs generados con el mismo
  patrón en trabajador.service.integration.test.ts y contrato.service.integration.test.ts
  colisionaban (ambos producían 20000001000 para seq=1). Fix: contrato usa prefijo
  "21" → RUCs de la forma 21NNN111111. Patrón a replicar si se agregan más test files.

D2 — rollback test usa empresaId inválida como mecanismo de fallo.
  El spec pedía "rollback transaccional si falla cierre del previo". En la
  implementación actual, el cierre del previo no puede fallar (es un UPDATE, no
  tiene FK externa). El fallo más realista es en la creación del nuevo contrato
  por FK inválida. El test usa empresaId='empresa-inexistente-xyz' para forzar
  el error en tx.contrato.create y verificar que el previo sigue activo.

D3 — No se implementó validación de campos inmutables con error tipado.
  El spec pedía INVALID_STATE si se intentan cambiar trabajadorId, empresaId,
  regimenLaboral, fechaInicio. La implementación optó por excluirlos del schema
  (ActualizarContratoSchema no los expone) — Zod los ignora silenciosamente si
  vienen en el input (no Zod strict). La alternativa sería z.object().strict() o
  un refine que rechace. El comportamiento actual es seguro (los campos no se
  modifican) pero no explícito al llamador. Documentado para decisión del arquitecto.

PENDIENTES DETECTADOS

P1 — ActualizarContratoSchema ignora campos inmutables silenciosamente.
  Ver D3. Si el arquitecto quiere error explícito, agregar .strict() o un
  refinement que detecte claves de campos inmutables en el input.

P2 — cerrarContrato no valida que fechaFin >= fechaInicio del contrato.
  Se puede cerrar un contrato con fechaFin anterior a su fechaInicio.
  Semánticamente incorrecto. Corrección: agregar refine comparando con
  el contrato.fechaInicio. Se puede agregar en Fase 2 o como deuda menor.
