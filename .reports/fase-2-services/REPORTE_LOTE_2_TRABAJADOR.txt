DECISIONES DESVIADAS DEL PLAN ORIGINAL

D1 — migrate dev no disponible en entorno no-interactivo con warnings de constraint.
  Prisma 7 requiere TTY cuando hay warnings que necesitan confirmación.
  Solución: migrate diff → SQL manual → migrate deploy.
  Los procesos anteriores habían dejado advisory locks (pg_advisory_lock 72707369)
  que bloquearon intentos posteriores; se liberaron con pg_terminate_backend.
  Para lotes 3 y 4: si hay warnings en migrate dev, usar el mismo protocolo.

D2 — planilla.service.integration.test.ts actualizado.
  crearTrabajador() ahora requiere empresaId como parámetro obligatorio.
  Todos los call sites actualizados con e.id. Sin cambios de lógica de negocio.

D3 — DEFAULT '' en migración para columna NOT NULL con tabla vacía.
  Prisma genera NOT NULL sin DEFAULT en la migración; como la tabla estaba vacía
  se añadió DEFAULT '' temporal y luego se removió. El DEFAULT solo existe en la
  DDL de transición, no queda en el schema final.

PENDIENTES DETECTADOS

P1 — onDelete: Restrict en Trabajador→Empresa.
  Si se intenta eliminar (hard delete) una Empresa con trabajadores, Postgres lanza FK error.
  El soft-delete de Empresa no toca la FK, así que no hay problema en flujo normal.
  El motor de planillas usa empresaId en Contrato (que también tiene Restrict implícito).
  No hay acción en Fase 2.

P2 — agregarHijo no verifica que el trabajador no esté eliminado.
  Actualmente se puede agregar un hijo a un trabajador soft-deleted (findUnique sin filtro eliminadoEn).
  Semánticamente es incorrecto. Corrección mínima: verificar eliminadoEn en agregarHijo.
  Decisión: elevar para que el arquitecto decida si aplica en Fase 2 o en una revisión posterior.
  Para Fase 2 el path prioritario es la extracción de liquidacion.service.ts.
